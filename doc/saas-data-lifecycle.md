# 账号与团队删除运行说明

本轮移除业务数据导出、文件、头像及其存储清理模块。保留账号注销和团队删除，采用 Pundit 授权；登录仍由 Devise/JWT 负责。

## 删除申请与恢复

- 本人注销和团队 owner 删除团队均要求当前密码；取消也要求密码。
- 默认冷静期七天，DELETION_COOLING_DAYS 可配置为 1—30 天。
- 账号冷静期内可登录取消，但不能新建/加入团队或接任所有权；申请和执行均检查最后 owner。
- 团队申请后冻结写入；取消恢复之前状态。开始不可逆清理后不再允许取消或普通后台恢复。
- 阶段简化为 requested → ledger → records → completed；失败记录保留检查点，工作进程和超级管理员可重试。
- 清理成员、邀请、通知、邮件敏感内容和账号会话，匿名化主体；不再调用文件或导出服务。
- 审计清除个人元数据及自由文本原因，保留必要标识，默认保存365天。
- 完成通知使用申请时加密保存的邮箱，发送成功即清除；失败时最多保留到完成后30天。

## 独立删除台账

生产必须设置 DELETION_LEDGER_PATH，指向独立于数据库备份、持久且受限的目录。开发默认 storage/deletion-ledger。

不可逆决定提交后、实际清理前先将最小台账写入独立目录。文件保存请求 UUID、主体类型/ID、创建时间指纹和删除时间，不保存姓名或邮箱。写入失败时保持主体不可访问，等待修复后重试。

恢复顺序：

1. 关闭应用入口，恢复数据库并挂载最新独立台账。
2. 必要时运行 `bundle exec rails data:deletions:export`，从数据库补齐台账文件。这是恢复台账工具，不是已移除的业务导出 API。
3. 运行 `bundle exec rails data:deletions:replay`，按 Team → User 顺序重放。
4. 核对失败记录和账号状态；若恢复备份中的所有权需要人工修复，保持账号停用，修复后重新重放。
5. 重放成功后才恢复任务和流量。

## 模块移除迁移

保留历史迁移，新增前向迁移移除 documents、data_exports 和 users.avatar_document_id。旧 files/exports 删除检查点归并 records；清理已删除模块的队列记录、专属通知和附件关联元数据，避免运行不存在的类。

迁移不删除磁盘或对象存储文件内容。通用 Active Storage 表保留且公开路由关闭。需要处理历史文件实物时，应在确认业务保留要求后独立安排存储清理。本轮只在测试环境验证迁移，不自动清空开发或生产数据。
