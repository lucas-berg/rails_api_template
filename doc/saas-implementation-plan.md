# SaaS 通用模板五步实施计划

本文定义当前 Rails 模板的五步实施顺序、接口边界与验收条件。前三步组成首期团队协作版本；第四、五步完善内部使用和数据生命周期。步骤中的复选框仅在对应实现与测试证据齐全后勾选。

## 共同约定

- JWT 从签发起固定有效 90 天，访问不续期；退出、改密、封禁和远程撤销立即失效。
- User 是全局账号；Team 是租户；Member 是用户与团队的关系。统一使用 team_id、Current.team 和 `/api/v1/teams/:team_id`。
- 不使用 Pundit 或其他权限库。普通 Ruby 策略明确登记允许动作，缺少身份、未知资源或未知动作默认拒绝。
- 交付 JSON API、OpenAPI 和 ActiveAdmin；保留现有认证页面，不建设完整用户控制台。
- 用户验证邮箱后主动创建团队或接受邀请，不自动创建个人团队。
- 不包含套餐、付费权益、支付、计费用量、API Key、对外 Webhook、企业 SSO 或通用业务导入。
- 新接口使用 `{ data, meta }`；失败使用 `{ errors: [{ code, message, field }], request_id }`。401 未认证、403 无动作权限、404 不可见资源、422 校验失败、409 状态冲突、429 限流。
- 列表每页默认 20 条、上限 100，筛选和排序采用白名单。现有认证和资料接口保持原响应外壳。
- 时间存 UTC；默认语言 en。用户及平台管理员当前为 integer 主键，新外键必须匹配。
- 每个团队至少一位 owner；授权、成员和团队状态实时检查，不将长期角色快照写入 JWT。

## 第一步 账号认证与事务邮件

### 目标与依赖

基于现有 Devise、devise-jwt、GoodJob 和 SMTP，建立邮箱验证、可撤销的 API 会话及可靠邮件基础。此步不依赖团队表。

### 操作顺序

1. 添加 User 确认邮箱、待确认邮箱、账号状态和凭证版本字段，启用 confirmable/reconfirmable。确认链接有效 24 小时；未确认用户不能登录。开发历史用户不自动确认。
2. 邮箱变更校验当前密码，确认前保留旧邮箱，检查 uid 与邮箱同步时机。确认和密码重置请求保持防邮箱枚举语义。
3. 新建 AuthSession，存 jti 摘要、凭证版本、到期和撤销时间、最后访问时间及受限设备信息，不保存原始 JWT。
4. JWT 与 AuthSession 统一 90 天到期。仅为实际返回 JWT 的 JSON 登录建立记录；浏览器 Cookie 登录不产生 API 会话。
5. 请求校验账号状态、会话和凭证版本。退出仅撤销当前会话；密码修改、重置和封禁撤销全部旧凭证。Cookie 同样检查凭证版本，防止恢复账号后旧会话重新有效。
6. 提供会话列表和撤销；认证响应使用明确字段白名单，防止暴露新增的秘密字段。
7. 实现邮件专用 outbox，令牌更新和邮件意图同事务写入。Devise 原有 after_commit 通知需要调整到事务内登记意图，不能只在提交后创建 outbox。
8. GoodJob 负责发送、补投和有限重试；任务只接收 outbox ID，临时令牌内容加密，发送成功后清理。SMTP 不保证恰好一次，但重复发送不得重复改变业务状态。
9. 发件人和公开链接地址统一通过环境配置。暂时关闭用户硬删除及后台批量删除，直到第五步。

### 接口与数据

- 保留 `/users`、`/users/sign_in`、`/users/sign_out`、`/users/password`、`/api/v1/user`。
- 启用 `/users/confirmation` 验证和重发流程。
- 新增 `GET /api/v1/auth_sessions`、`DELETE /api/v1/auth_sessions/:id`，只能操作本人记录。
- 新表 AuthSession、MailDelivery；User 增加验证及凭证字段。

### 完成条件

- [ ] 注册、确认、重确认、找回密码与两个客户端会话分别通过请求测试。
- [ ] 90 天边界正确，访问不续期，注销和远程撤销即时生效。
- [ ] 改密、重置及封禁撤销全部旧凭证，恢复不会复活旧 Cookie。
- [ ] HTML 无幽灵 API 会话；JSON 不接受 Cookie 替代 Bearer。
- [ ] 回滚不发邮件；发送失败、任务重试及遗留任务补投可恢复。

## 第二步 团队与成员协作

### 目标与依赖

依赖第一步的认证及邮件能力，完成 Team、Member、权限、邀请和设置；关键审计在此步随业务事务接入。

### 操作顺序

1. 创建 Team、Member、Invitation、AuditEvent；建立非空、外键和唯一约束。Member 对 team_id/user_id 唯一，角色属于 Member。
2. 创建团队和首位 owner 同事务提交。团队列表从当前用户有效成员关系出发，不接受客户端指定资源归属。
3. 建立 Current.team 与新 API 基类。先认证、再解析可见团队、从团队关联加载资源、最后校验动作。任务传入团队 ID 并在完成后清理上下文。
4. 编写普通 Ruby TeamPolicy、MemberPolicy、InvitationPolicy 和集中 authorize! 入口。未知动作拒绝，写入前鉴权，服务复核团队归属及成员有效性。
5. 固定 owner/admin/member/viewer。owner 管理团队、角色和所有权；admin 仅管理设置及 member/viewer；member/viewer 可读团队目录，业务写权限随后续资源单独授权。
6. 邀请支持发送、查询、重发、撤销及接受。有效 7 天，只保存 token 摘要，重发轮换令牌。接受者必须登录且邮箱已验证并匹配。
7. 团队行锁串行保护角色变化、成员移除、邀请接受和所有权转移。转移对象必须为有效成员，原 owner 降为 admin；不得留下无 owner 团队。
8. 支持团队名称、语言、时区和个人偏好。全局 Setting 保持独立；首期无席位限制和商业配额。
9. 关键写操作与 AuditEvent 同事务，记录 actor、request_id、资源和白名单变化。为邀请邮件加入可选团队关联，发送前检查邀请仍有效。

### 接口与数据

- `GET/POST /api/v1/teams`；`GET/PATCH /api/v1/teams/:id`。
- `/api/v1/teams/:team_id/members` 列表及成员修改、移除。
- 团队下 invitations、settings、ownership_transfer；`POST /api/v1/invitations/accept`。
- 团队状态 active/suspended；暂停团队不能执行业务写入。

### 完成条件

- [ ] 创建、邀请、加入、角色修改和所有权转移形成完整闭环。
- [ ] 跨团队 ID、伪造 team_id、自我提权及 admin 管理 owner/admin 被拒绝。
- [ ] 邀请过期、撤销、错误邮箱、重发旧令牌和重复接受均正确处理。
- [ ] 并发不会创建重复成员或移除最后 owner；旧 JWT 随成员变化即时失权。
- [ ] 审计和邮件意图与业务回滚一致，设置仅暴露允许字段。

## 第三步 运营后台与首期运行保障

### 目标与依赖

依赖前两步，完成管理、审计查询、共享限流与运行说明。前三步整体验收后才发布首期版本。

### 操作顺序

1. AdminUser 使用 super_admin/support 两角色；已有开发管理员回填 super_admin，新账号默认 support。
2. 自定义 ActiveAdmin::AuthorizationAdapter，实现 authorized? 和 scope_collection。模型类、实例、Dashboard、自定义动作均明确授权，未知项默认拒绝。
3. 添加团队、成员、邀请、会话、审计和邮件投递查询页面，敏感字段不展示、不导出。support 所有入口只读。
4. 受控提供账号封禁/恢复、团队暂停/恢复和邮件重试，要求原因并调用业务服务；保留所有硬删除限制。
5. GoodJob、Flipper 独立挂载入口也检查 super_admin；不依赖 ActiveAdmin 页面权限间接保护。
6. 新增团队审计列表，仅 owner/admin 可用，按白名单筛选和分页。
7. Rack Attack 使用 Redis 共享计数。登录每 IP 每分钟 10 次；确认/重置分别每邮箱每 15 分钟 3 次；邀请每团队每小时 30 次。参数集中配置，429 返回 Retry-After。
8. 配置 CORS 白名单、敏感参数过滤及 request_id/job_id/team_id 日志关联；增加依赖就绪检查，保留原存活接口。
9. 同步开发、Docker 和 CI 的 Redis 配置；补充邮件、任务、数据库、限流存储故障及恢复操作说明。
10. 更新 schema、模型注释、OpenAPI，运行前三步全部回归和代码质量检查。

### 完成条件

- [ ] support 无法通过直接请求、批量入口、自定义动作或导出读取秘密/执行修改。
- [ ] 暂停团队禁止业务写入，封禁用户即时撤销凭证；操作可审计。
- [ ] 多进程共享限流生效，错误和就绪检查不暴露配置。
- [ ] 认证、隔离、角色、并发、邮件故障和后台测试整体通过。
- [ ] 模型注释、数据库结构、OpenAPI 与实现一致，运行及回滚说明齐全。

## 第四步 内部通知与私有文件

### 目标与依赖

首期验收后完善通知、文件和摘要 API，不新增完整用户控制台。

### 操作顺序

1. 新增通知、投递记录和偏好；用事件标识与接收人唯一约束去重，事务内登记待发送信息。
2. 提供本人通知列表、已读标记和可选通知偏好；安全通知不随营销/普通通知关闭。
3. 发送前检查成员关系和团队状态，已移除成员不能收到新团队信息；明确失败重试与语言回退。
4. Active Storage 外增加带 team_id 的文件业务模型，覆盖上传、完成、下载、预览和删除全过程授权。
5. 限制文件大小及类型，检查真实内容，隔离未验证文件；禁止默认 blob 路由或 signed ID 绕过业务权限。
6. 清理未完成上传，删除和存储清理幂等可重试；头像接入相同受控上传能力。
7. 提供团队摘要和首次使用状态 API，从授权 scope 汇总角色、成员及待办；后台提供相应查询。

### 完成条件

- [ ] 本人消息隔离、成员移除、通知偏好、重复事件和失败重试通过测试。
- [ ] 跨团队文件、signed ID、直接存储路由及未验证文件均无法绕过权限。
- [ ] 非法内容、上传中断、重复删除和孤儿文件清理行为明确。
- [ ] 团队摘要仅使用授权数据，无完整用户控制台或计费用量系统。

## 第五步 数据导出与删除流程

### 目标与依赖

依赖权限、审计、任务、通知及私有文件，建立可恢复的数据退出流程。通用业务导入不属于本轮。

### 操作顺序

1. 新增导出记录，包含团队、发起者、进度、失败原因、私有结果及过期时间；异步导出已定义的团队数据。
2. 执行导出与下载结果时分别复核身份、成员和角色；结果短期有效，到期删除。CSV 如有使用需防公式注入。
3. 账号注销和团队删除分别建立申请、排期、执行、完成、取消及失败恢复状态。明确冷静期和不可撤回节点。
4. 账号注销前校验最后 owner，要求先转移所有权。团队删除冻结写入，撤销会话/邀请等可继续访问或创建数据的入口。
5. 制定保留及清理表，依序处理成员、邀请、通知、文件、导出结果和任务；审计按独立策略受限保留。
6. 任务保存检查点，重复执行不产生重复副作用；失败可续跑。删除台账在备份恢复后重放，防止已删除账号复活。
7. 把原账号删除入口接入统一申请服务，后台调用同一服务；增加申请、查询、取消、通知及人工重试入口。
8. 测试删除中断、导出时失权、恢复重放及孤儿清理，记录运行与恢复说明。

### 完成条件

- [ ] 任务执行前失权会停止导出，失权后无法下载已有结果；过期结果不可访问。
- [ ] 唯一 owner 不能直接注销，删除申请可在执行前取消。
- [ ] 删除中断可恢复，重复任务不会重复破坏数据；凭证不能继续访问。
- [ ] 私有文件、通知、待处理任务和导出结果纳入清理；恢复后重放删除台账。

## 提交与验证策略

按可审查单元分别提交：实施文档、认证与邮件、团队权限及邀请、后台与运行保障、通知、私有文件、数据导出、删除生命周期，以及必要的集成修复。跨模块功能尚未通过整体验收时不标记完成。

每批执行针对行为的 RSpec；首期及最终交付执行完整测试、代码分析、模型注释和 OpenAPI 一致性检查。测试覆盖拒绝路径、并发、任务重试和兼容，而不只覆盖正常响应。文档与代码一起更新，但保留用户无关改动。

实现和验收证据另见后续运行记录；本文件描述目标，不代表目标已经实现。
